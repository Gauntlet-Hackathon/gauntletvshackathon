## Wave 0 decisions the tickets did not specify
Made by the integrator while turning the plan into contracts. Reverse any of them with a ticket.

**Tooling and layout**
- Python packages are `rescue_shared` (shared/), `rescue_field` (field/), `rescue_engine` (engine/), `rescue_evals` (evals/). Pytest finds them through `pythonpath` in `pyproject.toml`; there is no pip-installable root package.
- `pyproject.toml` has no `[project]` table. Dev tools (`pytest`, `ruff`) are a PEP 735 dependency group installed with `pip install --group dev`. Ruff covers `shared field engine evals` (not `cloud` or `.github`); it runs lint only, no format check. Line length 100.
- Pytest runs with `-m 'not slow'` by default, so local runs and CI both skip `slow` tests; `pytest -m slow` runs them.
- `constraints.txt` pins every package installed today plus `psycopg`/`psycopg-binary` (nobody installs it yet); each lane's `requirements.txt` starts with `-c ../constraints.txt`.
- `progress/<lane>.md` files exist (with a header) so agents append a line instead of creating the file.
- CI has three jobs (`python`, `cloud`, `test`). `test` is the aggregate and is the check that branch protection requires.
- The cloud skeleton was generated by `mix phx.new` with its defaults (Tailwind, daisyUI, gettext, LiveDashboard in dev). Its generated `cloud/AGENTS.md` is kept as the Phoenix coding guide. `/health` returns `{"status":"ok","time":…}` without touching the database.
- Test database: `DATABASE_URL` without a database name gets `rescue_cloud_test` appended (so the same `postgres://postgres:postgres@localhost:5432` works for CI and local).

**Contracts**
- IDs are 26-character ULIDs; timestamps are UTC with `Z` and seconds precision; both are enforced by regex in the schemas and models.
- `rules_version` = `rules@<7–40 hex>+bin:<8–64 hex>`; `model_version` = `hf:<org>/<repo>@<7–40 hex>` or `stub:<name>` (`shared/rescue_shared/versions.py`). `rules_version` and `model_version` on the event envelope may be null (cloud-made `corrected` events have neither).
- `extracted` payload additions: `needs[]` items are `{kind: food|water|meds, hours_without: number|null}` (no confidence), `request_kind` is a plain enum with no confidence. `people_count.value` and `location.text` may be null. `spans[].label` is upper-case.
- `engine_input` = `{extracted, context}`; `context` = `duplicate_candidates`, `street_list_hits` (list of matched street/landmark strings), `hoax_marker_hits` (number), `thresholds` (10 named numbers). `decided` payload = `{engine_input, engine_output}`.
- `engine_output.follow_up_question` is required exactly when the outcome is `abstain`, and also set on a `prioritized` result whose tier was raised by an uncertain signal.
- Sync API additions: `/sync/events` returns `{acked, rejected}` (rejected = failed validation, never retried unchanged); `/sync/down?since=<n>` uses the cloud's integer sequence number and returns `next_since`; max 200 events per batch (400 above); error bodies are `{"error": code, "detail"?}`.
- Shared logic beyond the ticket's list: `normalize_contact`, `street_list_hits`, `duplicate_groups` and `vulnerable_count` in `rescue_shared.logic`, `rescue_shared.contracts_io` for loading schemas, and `contracts/logic.md` as the logic spec.

**Rubric clarifications** (all in `contracts/engine_rules.md`; `docs/plan/04-decision-rubric.md` itself is unchanged)
- Evaluation order: request check → hoax → location → tier → duplicates/contradictions. 04 numbers hoax last; here it comes second so a prank is never ranked.
- Boundaries: a confidence at the minimum passes (`≥`). Uncertain band is 0.5 ≤ c < 0.75; 0.75 and above is firm.
- `low_confidence_hazard` (03 lists it, 04 never says when): a hazard or vulnerability with confidence 0.25–0.5 that would raise the tier abstains with a confirm question; below 0.25 is ignored.
- `possible_hoax` = at least 1 marker hit **and** `is_request` confidence below 0.85. A "clearly old post" (`is_stale_post`, confidence ≥ 0.6) is `not_a_request`.
- Defaults the rubric does not state: `request_kind == rescue` with no other trigger is P2 (stranded people); anything else with no trigger is P3. A hazard such as `rising_water` alone is P2. P1 "infant/elderly/disabled + rising water" means vulnerable kind `child`, `elderly` or `disabled`.
- Duplicates: same normalized location within 12 hours, and either the same contact or the same known people count; `conflicting_counts` fires when the contact matches but the counts differ. A duplicate keeps the highest tier of its candidates and itself.
- All follow-up question texts are fixed strings (see `contracts/engine_rules.md`).

**Fixtures**
- `expected` outputs in `contracts/fixtures/cases.jsonl` and the expected values in `contracts/vectors/*.json` were written by hand from the rubric and the spec files, then checked by tests only for internal consistency, never produced by code.

## Model output format (H1a)
Decided 2026-11-07 (H11, #177) from the SLM trainer's answer, relayed by Paawan.
- **Model type:** an encoder tagger plus heads, not a generative model. The whole model is fine-tuned; no LoRA or PEFT.
  - Primary: `convaiinnovations/laya-multilingual` @ `1720e3e`, an mmBERT-base (ModernBERT) encoder.
  - Challenger: `jhu-clsp/mmBERT-small` @ `abc3262`.
- **Library:** PyTorch with Hugging Face `transformers` (`AutoModel` for the encoder) and the trainer's own heads. The inference code is `src/rescue_tagger/{model,infer,labels,durations}.py` in the public repo [fastresponderSLM](https://github.com/Gauntlet-Hackathon/fastresponderSLM) @ `c287541`. The field app vendors these files (F25a, #188).
- **Versions:** torch 2.15.0, transformers 5.22.2, safetensors 0.8.0, huggingface_hub 2.4.0 and tokenizers 0.23.3, pinned in `constraints.txt`. They are installed only through `field/requirements-model.txt` in the field image (F32, #233), with torch taken from the CPU wheel index. CI never installs them, so its tests mock the model.
- **Checkpoint layout:** `encoder/` (save_pretrained), `tokenizer/`, `heads.safetensors`, `tagger_config.json`, and `calibration.json` (per-head temperatures). It loads with `infer.Extractor.load(folder)`.
- **Runtime:** CPU, 4 threads, deterministic, about 45-50 ms per message.
- **Span tags (BIO):** LOCATION, COUNT, TIME, NEED_DURATION, CONTACT. CONTACT is never put into the payload. `hours_without` is parsed from the NEED_DURATION span by code, not by the model.
- **Heads and labels:**
  - yes/no: `is_request`, `is_stale_post`
  - multi-label: `vulnerable`, `hazards`, `needs`
  - single-label: `request_kind`, `location_type`
  - `people_count`: 21 classes, where 0 means not stated and 1-20 are counts
  - Confidences are calibrated (temperature scaling) and truncated, not rounded.
  - The field app reports `location.confidence` as `min(location_type head, LOCATION span confidence)` (F39, #246; local change in `tagger/assemble.py`). A weak span with a confident type head would otherwise pass the engine's 0.6 location gate with a doubtful address; now it yields the follow-up question instead. The trainer's evals should match.
  - `hours_without` parsing (local change in `tagger/durations.py`, review PR-1 M-05/O-06): a number the parser cannot read ("1.2.3 hours", "1,2,3 days") gives `None` (it raised `ValueError` and lost the request), and hours are clamped to 8760 (one year), so a huge number is never `inf`. The trainer's `durations.py` should match.
- **Sample raw output** from the Laya checkpoint `train_laya-20261107-043427`. The input is a message the trainer wrote, not one from any eval set: "Please help, water is up to the roof at 4512 Bellfort Ave. My grandmother is 82 and on oxygen, 3 of us stuck in the attic since last night, no food or water for 2 days". The output passes `rescue_field.slm.validate_extracted`:
  ```json
  {"location": {"text": "4512 Bellfort Ave", "type": "address", "confidence": 1.0},
   "people_count": {"value": 3, "confidence": 0.971},
   "vulnerable": [{"kind": "elderly", "confidence": 0.997}],
   "hazards": [{"kind": "rising_water", "confidence": 0.66}, {"kind": "on_roof", "confidence": 0.961}],
   "time_ref": {"text": "since last night", "is_stale_post": false, "confidence": 0.999},
   "is_request": {"value": true, "confidence": 0.998},
   "spans": [{"start": 40, "end": 57, "label": "LOCATION"}, {"start": 95, "end": 102, "label": "COUNT"},
  ```

## Dataset licenses (H2)

**For the model trainer**
- Do not train the model published on Hugging Face on HumAID or any other CrisisNLP data. The [CrisisNLP Terms of Use](https://crisisnlp.qcri.org/terms-of-use.html) say "use the data only for research on humanitarian computing", "keep the contents of these dataset(s) confidential (you can always share the tweet-ids)" and delete the data "upon completion of the research (you can always keep the tweet-ids)" or on request (again keeping tweet IDs). A generative model can repeat tweet text, and a public model outlives "completion of the research".
- If a HumAID-trained model is published anyway: weights under CC BY-NC-SA 4.0, card marked non-commercial and research-only, HF gated access, HumAID cited, no training data shipped, and a check that it does not regurgitate training tweets.

- No later commercial use of any CrisisNLP/QCRI data or a model trained on it. A commercial version needs a model retrained on data we own or license.
- Publishing the model also depends on the base model's license and on the terms of whichever model generates synthetic golden set B (`docs/plan/05-evals.md`, row B). Those are not dataset licenses, but they affect HF publishing and commercial use; check both before H1b.

Where the CrisisNLP Terms of Use apply: the [CrisisNLP home page](https://crisisnlp.qcri.org/) says "Please carefully read our Terms of use before using resources available on this site."; QCRI's own HF loading script sets `_LICENSE = "https://crisisnlp.qcri.org/terms-of-use.html"` ([HumAID.py](https://huggingface.co/datasets/QCRI/HumAID-all/blob/main/HumAID.py)); and HumAID was collected by QCRI's AIDR system. ## Step 3 review fixes (2026-11-07)
Findings R1–R13 (engine rules) and A1–A12 (agent assumptions) are in the step 3 review. Paawan approved fixing them; where a finding needed a product call, the option below was chosen. These supersede the conflicting Wave 0 lines above.

**Engine rules**
- R1: every `abstain` carries `provisional_tier` (P1/P2/P3): the step-4 tier computed with firm, uncertain and weak signals together (the most cautious reading), whatever the abstain cause. Other outcomes have `provisional_tier: null`. Boards sort follow-ups by `provisional_tier`, then by the within-tier key. Version skew: `engine_output.schema.json` stays strict (the key is required, so new engines must emit it), but the cloud accepts a decided `engine_output` that lacks the key as `provisional_tier: null`, for every outcome, so events queued on a pre-upgrade field build are not rejected for good; a present key is checked strictly. The cloud `/records` list ranks an abstain at its `provisional_tier` (a "P1?" with the P1 rows, after the ranked P1s) and its tier filter matches either column.
- R2: a weak (0.25–0.5) signal that would raise the tier no longer abstains a request that is already P1 or P2: it stays `prioritized` at that tier with the `low_confidence_hazard` question as its follow-up. It still abstains `low_confidence_hazard` when the request would otherwise be P3. (Replaces the `low_confidence_hazard` line above.)
- R3: the hoax check moves after tiering. A possible hoax whose tier is P1 stays `prioritized` with the `possible_hoax` question as follow-up; P2/P3 still abstain `possible_hoax`. Default thresholds and the marker list are unchanged. (Replaces "hoax comes second".)
- R4: `conflicting_counts` stays an abstain, but now carries the tier via `provisional_tier` (R1), taken as the highest of the request and its candidates.
- R5: a stale post whose tier would be P1 abstains `low_confidence_request` instead of being dropped as `not_a_request`.
- R6: extraction convention: any acute medical emergency (unconscious, not breathing, chest pain, severe bleeding, someone drowning) is extracted as hazard `injury`. R-P1-04 stays as the plan states it (child, elderly, disabled).
- R7: count-only duplicate matching needs the same known count **and** a count of at least 3; same-contact matching is unchanged.
- R8: thresholds must satisfy `hazard_weak_min ≤ hazard_uncertain_min ≤ hazard_firm_min`; engines exit 1 otherwise.
- R9: a duplicate whose own uncertain signal set the group tier keeps the confirm question. It also keeps its own question when its `weak_tier` is above the group tier, so a weak P1 hint on a P2 duplicate keeps the `low_confidence_hazard` question (PR #181 review, B1).
- R10: `duplicate_of` is the oldest direct candidate and may be an intermediate member; consumers resolve groups with `duplicate_groups`.
- R11: an `address` or `coords` location with null or blank text counts as no usable location.
- R12: conflicting *locations* across duplicates are not detected (04:33 asks for it). Deferred: the candidate shape cannot express it. Recorded here as a known deviation.
- R13: when the weak signal that triggers `low_confidence_hazard` is a vulnerable person, the follow-up asks whether a child, elderly or disabled person is present.

**Cross-lane**
- A1: status order is assigned < escalated < rescued (escalation follows an assignment), in field and cloud alike; written into `contracts/logic.md`.
- A2: `build.py` stamps the real `rules_version` into the built engine, so emitted decisions carry it and replay can find the build.
- A3: the evals runner writes `metrics["calibration.ece"]` (one ECE pooled over every extracted-field confidence the decision is made from; engine output has no confidence of its own) for the promotion gate.
- A4: rejected events are stored as rejected and never re-sent unchanged; /sync/status shows their count.

## WINPATH-1: build folders drop the ':' (2026-11-07)

- A build lives in `engine/dist/<rules_version with ':' as '-'>/` (`rescue_shared.versions.dist_dirname`, `RescueCloud.Replay.dist_dirname/1`), not `engine/dist/<rules_version>/`: Windows cannot store ':' in a file name, so git refused every Windows checkout of main after H12 committed the frozen build.
- The rules_version itself is unchanged everywhere it is data: manifest.json, the stamped binary, events, contracts. The committed build was renamed, not rebuilt, so its bytes and hashes are the same.
- The field image now takes two build args: `RULES_VERSION` (reported) and `ENGINE_BUILD` (the folder); `field/tests/test_dockerfile.py` checks they agree.
- `shared/tests/test_portable_paths.py` fails if any tracked path contains a character Windows cannot store.

## Model delivery to laptops (2026-11-07)
The plan (02 "Model registry", 06 hours 12-15) has laptops pull approved models from the cloud registry on down-sync. For the hackathon the field app gets its model differently:
- The field image bakes the pinned revision in at build time (`HF_REPO` / `HF_REVISION` build args, F32 #233). At runtime the app never reaches Hugging Face (`HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`) and loads only `/models/current`.
- The cloud keeps the registry and the gate (`RescueCloud.Models.pull/3`, `evaluate/2`, `promote/2`; cloud/README.md). The order for #104 is: run the evals on the candidate, `promote` it on the cloud, and pin only an `approved` revision in the field image build. That last step is a manual rule: nothing checks that the image's `HF_REVISION` matches the cloud's approved version.
- Without both build args no model is baked in, and the app starts on the keyword fallback (its model_version `stub:keyword-extractor` shows on `/sync/status` and the board; F37's banner, #244, appears only when the build args are set and the model then fails to load).
- Not built: `GET /models/{version}` and fetching a model bundle. Down-sync already carries the approved `model_version` string, and the laptop stores it with the previous one for rollback (`field/rescue_field/downsync.py`), but nothing downloads or loads that version. A model change ships as a new field image. That is fine for one hosted demo device and is the next step for a real fleet.

## Rules that may drop a message without a human (H20 #271; Paawan, 2026-11-07)
Kept as written in contracts/engine_rules.md for the demo; the rules freeze (H12) stays in place.
- **Stale posts:** a post judged stale is `not_a_request` (`R-NAR-02`) unless its cautious tier is P1 (R5). A stale P2 is
  not shown to a human.
- **Confident "not a request":** `is_request=false` at high confidence is `not_a_request` (`R-NAR-01`) even when P1
  hazards are extracted, so news reports and thank-you posts that mention injuries do not reach the board.
- **Landmarks:** any `street_list_hits` > 0 makes a landmark location usable, even if the hit is unrelated to the
  landmark text.
Why: each change needs the freeze lifted, both engines changed, a new `engine/dist/` build and Sets B-D re-checked,
hours before the demo. After the hackathon, the recommended change is to send stale P2 posts and landmark-only
locations without a matching street to the follow-up queue (in line with "never lower priority because of uncertainty").
