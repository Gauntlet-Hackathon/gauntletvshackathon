# Cloud conventions

Read this before writing cloud code. It describes the app as generated in Wave 0 and the patterns every later cloud ticket follows.
`AGENTS.md` (also in this folder, generated by Phoenix) has general Phoenix 1.8 / Elixir / Ecto / HEEx rules; this file is about
this app.

## Versions and setup
- Generated with `mix phx.new cloud --app rescue_cloud --no-mailer` (Phoenix installer 1.8.16). Deps: Phoenix 1.8.16,
  Phoenix LiveView 1.2, Ecto SQL 3.13 + Postgrex, Bandit, Jason, Gettext, Tailwind 4 + daisyUI (assets). No mailer, no auth.
- Elixir 1.20.5 on OTP 29.1.2, pinned in `.tool-versions`. CI reads that file (`erlef/setup-beam`).
- `mix.lock` is committed. Add or upgrade deps only in your ticket, run `mix deps.get`, and commit `mix.lock`.
- Module prefix: `RescueCloud` (business logic) and `RescueCloudWeb` (web). OTP app: `:rescue_cloud`.
- Postgres: tests use `DATABASE_URL` when set (CI, agent runners). A URL without a database name, such as
  `postgres://postgres:postgres@localhost:5432`, gets `rescue_cloud_test` (plus `MIX_TEST_PARTITION` if set) as its database.
  Without `DATABASE_URL`, `config/test.exs` uses `postgres:postgres@localhost`.
- Before you open a PR: `mix format --check-formatted && mix compile --warnings-as-errors && mix test`.
  `mix precommit` (a generated alias) compiles with warnings as errors, unlocks unused deps, formats and tests.
- Generated assets (`priv/static/assets/`), `_build/`, `deps/` and `erl_crash.dump` are ignored by `cloud/.gitignore`. Never commit them.

## Module layout
```
lib/rescue_cloud/                    business logic: contexts, schemas, Repo (no Phoenix imports)
  application.ex                     supervision tree (Telemetry, Repo, PubSub, Endpoint)
  repo.ex                            RescueCloud.Repo
lib/rescue_cloud_web/                web layer
  endpoint.ex  router.ex  telemetry.ex  gettext.ex
  components/core_components.ex      function components (<.button>, <.input>, <.icon>, <.flash>, ...)
  components/layouts.ex              Layouts.app/1 (page wrapper), Layouts.flash_group/1
  components/layouts/root.html.heex  HTML skeleton
  controllers/                       controllers + one *_json.ex / *_html.ex view module per controller
  live/                              LiveViews (`RescueCloudWeb.<Name>Live`)
priv/repo/migrations/                migrations (create them with `mix ecto.gen.migration name`)
test/support/                        ConnCase, DataCase, and your own fixture modules
test/rescue_cloud/                   context tests          (mirrors lib/rescue_cloud)
test/rescue_cloud_web/               controller + LiveView tests (mirrors lib/rescue_cloud_web)
```
- A **context** is a plain module under `lib/rescue_cloud/<name>.ex` (for example `RescueCloud.Events`) that owns its Ecto
  schemas under `lib/rescue_cloud/<name>/`. Controllers and LiveViews call context functions; they never call `Repo` directly
  and never build queries.
- Wave 0 ships no contexts yet. The first ones are `RescueCloud.Events` (C1) and the device registry (C2).
- Routes: `GET /health` is in the `:api` scope (no session, no auth); `/` is a LiveView in the `:browser` scope. Put sync routes
  (`/sync/*`) in an `:api` scope behind the device-auth plug.

## Function components, no Phoenix.View
- Templates are HEEx: `~H` sigils or `.html.heex` files embedded with `embed_templates`. `Phoenix.View` is not used and not installed.
- Shared UI goes in `RescueCloudWeb.CoreComponents` (already imported everywhere via `use RescueCloudWeb, :html`), or in a new
  module of function components that you add to `html_helpers/0` in `lib/rescue_cloud_web.ex`.
- A function component is a function that takes `assigns`; declare its inputs with `attr` and `slot`:
  ```elixir
  attr :status, :atom, required: true, values: [:active, :stale, :offline]
  attr :rest, :global

  def status_badge(assigns) do
    ~H"""
    <span class={["badge", @status == :offline && "badge-error"]} {@rest}>{@status}</span>
    """
  end
  ```
- Every LiveView template starts with `<Layouts.app flash={@flash}>` (see `RescueCloudWeb.DashboardLive`). Put unique DOM ids on
  elements you will assert on in tests.
- Controllers render HTML through a `*HTML` module (`use RescueCloudWeb, :html`) and JSON through a `*JSON` module, or call `json/2`.

## JSON handling
- `Plug.Parsers` (in `endpoint.ex`) decodes `application/json` bodies with Jason into `conn.body_params` / `conn.params`, with **string keys**.
  A body that is not valid JSON raises `Plug.Parsers.ParseError`, which Phoenix renders as 400 through `ErrorJSON`.
- Respond with `json(conn, map)` (see `HealthController`) or `put_status(conn, 422) |> json(%{error: "..."})`. Atom keys in the map
  are fine; they are encoded as strings.
- Sync API errors are always `{"error": "<machine_code>"}` with an optional `"detail"` (see `contracts/sync_api.md`).
  `ErrorJSON` produces `{"errors": {"detail": ...}}` for framework-raised errors; do not copy that shape for sync routes.
- Timestamps on the wire are UTC ISO 8601 with a `Z` and seconds precision (`2026-11-07T14:02:11Z`). Use `:utc_datetime` fields
  and `DateTime.from_iso8601/1`. IDs (`event_id`, `request_id`) are 26-character ULID strings; use `:string` columns, never `:binary_id`.
- Event `payload` and the engine input/output are stored as `:map` (jsonb) with string keys. Do not atomize incoming keys
  (`String.to_atom/1` on request data is forbidden).
- Validation: cast the envelope with an Ecto changeset (embedded schema or the `Event` schema), validate `payload` per `type`, and check
  it against the shared example files in `contracts/examples/` (valid files must give `valid?: true`, invalid files `valid?: false`;
  `contracts/vectors/*.json` must pass for `normalize_location` and duplicate grouping). Do not hand-write copies of those cases.

## Device-auth plug pattern
Status: the plug itself is ticket C2; Wave 0 only fixes the pattern so C2, C3, C8 and C9 agree. Decision: one bearer token per device,
read from `config/devices.exs` (see `docs/DECISIONS.md`).
- `RescueCloudWeb.Plugs.DeviceAuth` (in `lib/rescue_cloud_web/plugs/device_auth.ex`) is a module plug. It reads
  `authorization: Bearer <token>`, compares it in constant time (`Plug.Crypto.secure_compare/2`) with the configured tokens, and on
  success calls `assign(conn, :device_id, device_id)`.
- On failure it halts with `401` and `{"error": "unauthorized"}` (missing, malformed or unknown token). Body device ids that differ from
  `conn.assigns.device_id` get `403` `{"error": "device_mismatch"}`.
- It is attached with a dedicated pipeline, so `/health` stays public:
  ```elixir
  pipeline :device_api do
    plug :accepts, ["json"]
    plug RescueCloudWeb.Plugs.DeviceAuth
  end

  scope "/sync", RescueCloudWeb do
    pipe_through :device_api
    post "/heartbeat", SyncController, :heartbeat
    post "/events", SyncController, :events
    get "/down", SyncController, :down
  end
  ```
- Controllers take the device from `conn.assigns.device_id`, never from the request body.
- Tests set the header with `put_req_header(conn, "authorization", "Bearer " <> token)` (a helper in `ConnCase` or a test-support module),
  and configure test tokens in `config/test.exs`, not in `config/devices.exs`.

## How to write tests
General: `use ExUnit`, `async: true` unless a test touches global state. Never `Process.sleep/1`; use `start_supervised!/1`, `assert_receive`
and `:sys.get_state/1` (see `AGENTS.md`). Test files are named `*_test.exs` and mirror the `lib/` path.

**Ecto SQL sandbox.** `config/test.exs` sets `pool: Ecto.Adapters.SQL.Sandbox`. `RescueCloud.DataCase` and `RescueCloudWeb.ConnCase` both start a sandbox
owner per test (`RescueCloud.DataCase.setup_sandbox/1`), so every test sees an empty database and changes roll back. Use `async: true`.
A process that you start yourself and that touches the database (a GenServer, a Task) needs `Ecto.Adapters.SQL.Sandbox.allow/3`, or run
the test with `async: false`, which uses shared mode.

**Context test** (`test/rescue_cloud/events_test.exs`, `use RescueCloud.DataCase, async: true`): call the context function, assert on the
returned structs and on `errors_on(changeset)`:
```elixir
defmodule RescueCloud.EventsTest do
  use RescueCloud.DataCase, async: true

  alias RescueCloud.Events

  test "append/1 rejects an envelope without an event_id" do
    assert {:error, changeset} = Events.append(%{})
    assert "can't be blank" in errors_on(changeset).event_id
  end
end
```
Build test data with plain helper functions in `test/support/*_fixtures.ex` (`def event_fixture(attrs \\ %{})`) that call the context.
`test/support` is compiled only in `:test`.

**Controller test** (`test/rescue_cloud_web/controllers/health_controller_test.exs`, `use RescueCloudWeb.ConnCase, async: true`): use verified
routes (`~p"/health"`), the generated `get/post` helpers and `json_response(conn, status)`. For JSON POSTs pass a map: `post(conn, ~p"/sync/events", body)`
(ConnTest encodes it; set `put_req_header("content-type", "application/json")` when you send a pre-encoded string).

**LiveView test** (`test/rescue_cloud_web/live/dashboard_live_test.exs`, same `ConnCase`, plus `import Phoenix.LiveViewTest`): call
`live(conn, ~p"/")` for the connected mount (`get(conn, ~p"/")` checks the static render), then `has_element?/3`,
`element/3 |> render_click/1`, `form/3 |> render_submit/1` and `render/1`. Select by the DOM ids you put in the template, not by text layout.
For pushed updates, subscribe the test to the same `Phoenix.PubSub` topic and assert with `assert_receive`, then `render(view)`.
